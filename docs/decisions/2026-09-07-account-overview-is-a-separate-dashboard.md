# The account overview is a separate dashboard, and sums nothing across runs

Date: 2026-09-07
Status: Accepted

## Context

The Strategy dashboard is scoped to one `run_id`, so an operator watching
several concurrent runs in one account had to keep a browser tab per run
(issue #100). Two questions had to be settled before building anything: where
the view lives, and what it is allowed to compute.

`architecture.md` already draws the second line. A run maps its single account
to one order-adapter instance, and while a caller may group runs for reporting,
"combined PnL, Sharpe, drawdown, and reporting-currency conversion remain
caller-owned". The FX precedent in issue #87 says the same: Librae has no
reporting-currency model, so any figure that adds two currencies would be
invented rather than measured.

## Decision

**A separate dashboard, not a panel on the Strategy dashboard.** The Strategy
dashboard's variables and every one of its panels are scoped by `run_id`.
Adding a cross-run table would mean either a panel that ignores the dashboard's
own primary variable, or relaxing that variable for every other panel. A
separate dashboard keeps each one internally consistent, and its own variables
(currency, account, modes) express the scope this view actually needs.

**Same currency by construction, not by convention.** The currency and account
variables are single-select, so no query can span two currencies or two
accounts. This is a property of the dashboard rather than a rule an operator
has to remember.

**Per-run rows, no financial aggregation.** Equity, exposure, concentration
and open-position count are reported per run and never summed, averaged, or
ranked across rows. Portfolio-level Sharpe and drawdown are absent for the same
reason. Tests assert the absence — that no `SUM` over equity, no
`strategy_performance` join, and no Sharpe or drawdown column appears — because
this boundary is easier to erode by a later well-meaning addition than to
notice missing.

**Open positions are reconstructed at each run's own equity timestamp,** not at
"now", so a row cannot mix an equity value from one moment with a position
count from another. The reconstruction reads the latest `position_events` row
per symbol at or before that timestamp, breaking ties on event order. The tie
needs care: `make_event_id` zero-pads its index to four digits, so a plain text
sort stops following write order past 9999 events, and comparing length first
restores it.

## Consequences

An operator comparing accounts or currencies opens the dashboard twice; that is
the intended cost of not inventing a conversion. Anyone wanting a portfolio
total still owns it, as `architecture.md` says.

The dashboard is generated by `generate_dashboards.py` like the other two, and
the checked-in JSON is verified against the generator, so it cannot drift into
a second source of truth.
